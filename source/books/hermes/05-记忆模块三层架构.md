# 五、记忆模块三层架构

> **结论先行**：Hermes 的记忆系统解决了 LLM 无状态的本质问题——LLM 本身不记得任何东西，必须在每次请求时重建上下文。Hermes 用三层记忆分别解决三类"记住"问题：**第一层（MEMORY.md/USER.md）解决"下次见面还认识你"**，**第二层（SQLite + FTS5）解决"找回过去做过什么"**，**第三层（技能文件）解决"记住怎么做"**。

---

## 三层记忆架构全览

```
┌─────────────────────────────────────────────────────────┐
│           Hermes 三层记忆架构                             │
├─────────────────────────────────────────────────────────┤
│  第一层：内置持久记忆（陈述性记忆）                       │
│                                                         │
│   MEMORY.md  → Agent 对环境/约定/工具特性的笔记          │
│   USER.md    → 用户偏好、工作风格、习惯                  │
│   容量限制：MEMORY.md ≤ 2200 字符，USER.md ≤ 1375 字符  │
│   存储位置：~/.hermes/memories/                         │
│   注入方式：session 开始时以"冻结快照"注入 system prompt │
│   更新时机：LLM 调用 memory 工具，或自动 flush           │
├─────────────────────────────────────────────────────────┤
│  第二层：会话历史检索（情景记忆）                         │
│                                                         │
│   存储：SQLite + FTS5 全文搜索索引                       │
│   位置：~/.hermes/state.db                              │
│   访问：LLM 主动调用 session_search 工具按需检索         │
│   写入：每轮对话结束时自动持久化；原文永久保留            │
├─────────────────────────────────────────────────────────┤
│  第三层：技能知识库（程序性记忆）                         │
│                                                         │
│   存储：~/.hermes/skills/**/*.md                        │
│   注入：按需加载为用户消息，system prompt 只含摘要索引    │
│   索引大小：每个技能约 60-100 字符，20 个技能 ≈ 2000 字符│
├─────────────────────────────────────────────────────────┤
│  （可选）外部记忆提供商（共 8 个）                        │
│   mem0 / Honcho / RetainDB / Supermemory /              │
│   Holographic / ByteRover / Hindsight / OpenViking      │
│   通过 MemoryManager 统一管理，prefetch 后注入 user 消息 │
│   任意时刻只能激活一个；内置 MEMORY.md 始终并行运行      │
└─────────────────────────────────────────────────────────┘
```

**第三层技能索引的大小**：技能以**两级缓存的紧凑索引**注入 system prompt，每个技能仅占一行（名称 + 一句话描述），不包含全文内容。LLM 看到索引后，当判断某技能与当前任务相关时，主动调用 `skill_view(name)` 加载完整 SKILL.md 内容，再按其中指令执行。索引大小取决于安装的技能数量：每个技能约 60-100 字符，20 个技能约 1500-2000 字符，对 system prompt 影响可控。进程内使用 LRU 缓存（`_SKILLS_PROMPT_CACHE`）避免每轮重新扫描文件系统；重启后通过 `~/.hermes/.skills_prompt_snapshot.json` 磁盘快照（mtime/size 比对）加速恢复。

```
# 注入 system prompt 的紧凑索引实际格式（build_skills_system_prompt() 输出）：

## Skills (mandatory)
Before replying, scan the skills below. If one clearly matches your task,
load it with skill_view(name) and follow its instructions. ...

<available_skills>
  creative:
    - ascii-art: Generate ASCII art from text or images
    - manim-video: Create mathematical animations with Manim
  devops:
    - docker-management: Manage Docker containers and images
    - webhook-subscriptions: Subscribe to webhook events
  github:
    - github-pr-workflow: End-to-end PR creation and review workflow
    - github-issues: Create and manage GitHub issues
  mlops:
    - huggingface-hub: Browse and download models from HuggingFace
</available_skills>

If none match, proceed normally without loading a skill.

# 每个技能只有一行：- 名称: 一句话描述
# 全文内容不在 system prompt 里；LLM 调用 skill_view(name) 时才按需加载完整 SKILL.md
```

```
请求 build_skills_system_prompt()
        │
        ▼
第 1 级：进程内 LRU dict（_SKILLS_PROMPT_CACHE）
        │  key = (skills_dir路径, 工具列表, toolset列表, 平台)，最多缓存 8 个不同 key
        │  命中 → 直接返回字符串，零 I/O
        │  未命中 ↓
        ▼
第 2 级：磁盘快照（~/.hermes/.skills_prompt_snapshot.json）
        │  有效性验证：对比每个 SKILL.md 的 [mtime_ns, size]
        │  命中 → 跳过文件解析，直接从预解析元数据拼字符串
        │  未命中 ↓
        ▼
冷启动路径：完整文件系统扫描
        │  读取每个 SKILL.md → 解析 frontmatter → 提取 description
        │  写入磁盘快照（供下次进程重启后复用）
        │  写回 LRU dict
        ▼
返回最终索引字符串（注入 system prompt）
```

**缓存失效规则**：磁盘 snapshot 的有效性由 `_build_skills_manifest()` 判断——对每个 `SKILL.md` 记录 `[mtime_ns, size]`，只要有任意一个文件被修改/新增/删除，整个 snapshot 自动失效，触发冷启动全量重扫并覆写新 snapshot。LRU dict 最多缓存 8 个不同 `(skills_dir, tools, toolsets, platform)` 组合，超出后淘汰最久未用的条目（`OrderedDict` + LRU 策略）；多平台 gateway 同时服务时，不同平台的索引各自独立缓存，互不干扰。

## 第一层：内置持久记忆（MEMORY.md / USER.md）

**做什么**：两个 Markdown 文件分别存储 Agent 自己的笔记和用户画像。每次新会话开始时，这两个文件的内容以"冻结快照"形式拼入 system prompt，LLM 从第一条消息起就"认识"当前用户和当前环境。两个文件各有严格的**字符上限**（而非 token 上限，因为字符计数与模型无关，不同 tokenizer 下 token 数差异显著）：MEMORY.md 上限 2200 字符（约 800 tokens），USER.md 上限 1375 字符（约 500 tokens）。

```
两个文件的分工：
MEMORY.md = "Agent 的工作笔记本"（上限 2200 字符）
  存储：项目约定、工具特性、解决过的问题
  例："Python 项目使用 uv 管理依赖，测试命令是 pytest -v tests/"
       "用户的 Docker Desktop 有时候需要重启才能 pull 成功"

USER.md = "用户画像"（上限 1375 字符）
  存储：用户偏好、沟通风格、工作习惯
  例："用户偏好简洁回答，不喜欢废话和过多解释"
       "工作目录通常在 ~/projects，代码风格遵循 Google Style Guide"
```

**为什么分两个文件？** 职责分离让 LLM 写入时更容易判断放哪个文件（环境事实 vs 用户偏好），也便于未来分别调整容量配置、生命周期策略。

**写入流程（memory 工具）**：

```python
# LLM 调用示例
# target 参数指定写入哪个文件："memory" → MEMORY.md，"user" → USER.md
memory(action="add",     target="memory", content="项目使用 uv，不是 pip")

# replace/remove 使用 old_text 子字符串匹配定位条目（不是精确键名匹配）
# old_text 只需是目标条目的任意子字符串，LLM 无需提供完整条目内容
memory(action="replace", target="memory", old_text="uv，不是 pip", content="项目使用 uv 管理依赖，poetry 已弃用")
memory(action="remove",  target="memory", old_text="Docker Desktop 有时")

# 注意：memory 工具不存在 "read" action
# 记忆内容已在会话开始时自动注入 system prompt，LLM 直接从上下文中读取
# （工具响应始终反映磁盘的实时状态，与 system prompt 快照无关）
```

**replace/remove 的匹配逻辑（子字符串匹配）**：  

- 命中 0 条 → 返回 `"No entry matched"` 错误  

- 命中多条且内容相同（精确重复）→ 只操作第 0 条，安全  

- 命中多条且内容不同 → 返回 `"Multiple entries matched, be more specific"` 错误，并附上各条目前 80 字预览，要求 LLM 提供更精确的 `old_text`  

**去重机制**：`load_from_disk()` 读取文件后用 `dict.fromkeys()` 去重（保留首次出现、去掉精确重复条目）；`add()` 时对精确重复做预判，直接跳过并提示 `"Entry already exists"`。注意：去重仅针对精确重复的完整条目，语义相似但文字不同的条目不会被合并。

**容量超限时的处理**：执行 `add` 操作时，系统预先计算新总长度；若超限，直接返回错误并提示当前用量和超出量，要求先 `replace`/`remove` 腾出空间。`replace` 同样做超限检查，确保替换后不超容量上限。

```python
# tools/memory_tool.py - MemoryStore.add()
if new_total > limit:
    return {
        "success": False,
        "error": (
            f"Memory at {current:,}/{limit:,} chars. "
            f"Adding this entry ({len(content)} chars) would exceed the limit. "
            f"Replace or remove existing entries first."
        ),
        "current_entries": entries,
        "usage": f"{current:,}/{limit:,}",
    }
```

**关键设计：冻结快照（Frozen Snapshot）**

```
会话开始：
  MEMORY.md 内容 → 拼入 system prompt（快照冻结，本会话不变）
      │
      │ 对话中途，LLM 发现新知识
      ▼
  memory(action="add", content="新知识")
      │
      ├── 立即写入磁盘（持久化）
      └── 不修改当前 system prompt（保持提示缓存有效）
      
      │ 本次会话结束
      ▼
  下次会话开始：
  重新读取 MEMORY.md → 新知识进入 system prompt 快照
```

为什么用"冻结快照"而不是实时更新？如果每次写入记忆都重建 system prompt，Anthropic prefix cache 就会失效，导致每轮都全量计费（通常 2000~8000 token）。冻结快照保证 system prompt 在整个会话内稳定，prefix cache 持续命中，**最多可将缓存命中部分的输入 token 成本降低约 90%**（Anthropic prefix cache 命中按原价 10% 计费）。实际节省幅度取决于 cache 命中率，系统设计目标是让 system prompt 前缀在整个会话内保持不变以最大化命中。  

**本次会话写入的记忆，当前会话能立即看到吗？** 不能——但这是设计意图而非缺陷：磁盘立即持久化（原子写），LLM 在工具响应结果里能看到最新条目，而 system prompt 快照不变；下次 `AIAgent.__init__()` 时重新读取文件，新内容才进入快照。

**安全扫描**（防止提示注入攻击）：每条记忆写入前都会经过安全扫描，匹配以下威胁模式的内容将被拒绝写入。扫描范围不限于下方展示的 3 条规则，还包括凭据泄露、SSH 后门等模式，以及不可见 Unicode 字符检测。

```python
# tools/memory_tool.py（威胁模式示例，非完整列表）
_MEMORY_THREAT_PATTERNS = [
    (r'ignore\s+(previous|all|above|prior)\s+instructions', "prompt_injection"),
    (r'you\s+are\s+now\s+', "role_hijack"),
    (r'system\s+prompt\s+override', "sys_prompt_override"),
    # 还包括：凭据泄露、SSH backdoor、不可见 Unicode 字符等模式
]
# 写入前扫描：任何匹配到威胁模式的内容都会被拒绝写入
```

**多 profile 下的记忆隔离**：记忆文件路径通过 `get_memory_dir()` 动态解析（调用 `get_hermes_home()` 读取 `HERMES_HOME` 环境变量），不同 profile 的 `HERMES_HOME` 各不相同，因此各 profile 的记忆文件完全隔离，互不干扰：

```
~/.hermes/memories/MEMORY.md                    ← 默认 profile
~/.hermes/profiles/coder/memories/MEMORY.md     ← coder profile
~/.hermes/profiles/work/memories/MEMORY.md      ← work profile
```

### 自动记忆 Flush（防止信息在压缩中丢失）

**做什么**：在上下文压缩前，让 LLM 主动决定哪些信息值得长期保存，避免重要细节随中间轮次的摘要被淡化甚至丢失。

**触发条件**：

- 上下文压缩前自动触发（`min_turns=0`，强制执行）
- 周期性轮次触发（每隔 N 轮对话，LLM 主动复盘是否有新知识值得保存；N 可通过 config.yaml 配置，默认 6 轮，设为 0 可禁用）

```
flush_memories() 流程：

在 messages 末尾追加临时 flush 提示消息（含 sentinel 边界标记）
    │  "Review our conversation. Save important facts, user preferences,
    │   and project conventions to memory. Use the memory tool now."
    │  只暴露 memory 工具（其他工具从 schema 中移除）
    ▼
调用辅助 LLM（较廉价模型，temperature=0.3；具体模型可通过 aux_model 配置）
    │  LLM 扫描对话，判断哪些内容值得保存
    │  若无新知识，LLM 可以选择不调用任何工具（flush 流程仍正常结束）
    ▼
LLM 调用 memory 工具写入 → 持久化到磁盘
    ▼
用 sentinel 标记找到临时消息的边界 → pop 掉临时消息
    │  原始 messages 列表不受污染
    │  flush 过程中 LLM 产生的所有输出（含工具调用）均在边界内，一并清除
    ▼
（注意：本次会话的 system prompt 不变；新内容下轮生效）
```

**flush 调用的辅助 LLM 如何配置？** `flush_memories()` 优先通过 `call_llm(task="flush_memories")` 调用辅助 LLM，模型由 `config.yaml` 的 `auxiliary.flush_memories` 节点决定。若未配置，系统走 auto 提供商自动选择逻辑（通常选当前可用的较廉价模型）；若辅助 LLM 不可用，回退为主提供商直接调用，以 `temperature=0.3`、`max_tokens=5120` 发起请求。

```yaml
# ~/.hermes/config.yaml
auxiliary:
  flush_memories:
    provider: "anthropic"          # 可选，不填则 auto
    model: "claude-haiku-4-5"      # 可选，不填则 auto 选较廉价模型
    timeout: 30                    # 可选，默认 30 秒
memory:
  flush_min_turns: 6   # 满 N 轮对话才触发周期性 flush（0 = 禁用）
```

**如果 LLM 判断没有值得保存的信息，会怎么做？** 什么都不做，静默完成。flush 提示词只是请求"如果有就保存"，LLM 若认为无新知识，就不调用 `memory` 工具，`flush_memories()` 收到的 `tool_calls` 为空，直接进入 `finally` 清理 sentinel 并返回。即便 LLM 不写任何东西，flush 调用只多一次辅助 LLM 请求（较廉价），不会有额外副作用。

**sentinel 标记的技术细节**：sentinel 是格式为 `__flush_{id(self)}_{time.monotonic()}` 的唯一字符串（如 `__flush_140234567890_12345.678901`）。`id(self)` 确保不同 AIAgent 实例之间不冲突，`time.monotonic()` 确保同一实例的多次 flush 之间不冲突。之所以用字符串比较而非对象 identity（`is`），是因为 messages 列表可能经过序列化/反序列化（dict copy、JSON 往返），对象 identity 不可靠，字符串比较更稳健。

```python
# run_agent.py
_sentinel = f"__flush_{id(self)}_{time.monotonic()}"
flush_msg = {"role": "user", "content": flush_content, "_flush_sentinel": _sentinel}
messages.append(flush_msg)

# finally 块：无论是否有工具调用，都清理临时消息
finally:
    while messages and messages[-1].get("_flush_sentinel") != _sentinel:
        messages.pop()
    if messages and messages[-1].get("_flush_sentinel") == _sentinel:
        messages.pop()
```

## 第二层：会话历史检索（session_search）

**做什么**：将所有历史对话存入 SQLite + FTS5 全文搜索索引，让 LLM 在遇到"我上次怎么解决这个问题"时，通过 `session_search` 工具主动检索过去的对话，而不需要用户重复说明背景。**存储内容为完整原始消息，不截断，不摘要**——`append_message()` 直接将 `content` 字段原文写入，旧 session 封存后消息一行不动，始终可搜。唯一可能截断的情况是超长工具结果（默认 100000 字符上限，超出后加 `[TRUNCATED]` 标记，属极端情况）。

**数据库结构**：

```sql
-- 数据库文件实际路径：~/.hermes/state.db（注意：不是 hermes_state.db）
-- hermes_state.py 是源码模块名，对应的数据库文件名为 state.db

CREATE TABLE sessions (
    id TEXT PRIMARY KEY,         -- UUID v4
    source TEXT NOT NULL,        -- "cli" / "telegram" / "discord" 等
    model TEXT,
    started_at REAL NOT NULL,    -- Unix 时间戳
    ended_at REAL,
    system_prompt TEXT,          -- 快照存储（用于续接会话）
    parent_session_id TEXT,      -- 压缩链：上下文压缩后新旧会话的链接
    title TEXT,                  -- LLM 生成的会话标题（可选，唯一）
    input_tokens INTEGER DEFAULT 0,
    output_tokens INTEGER DEFAULT 0,
    estimated_cost_usd REAL      -- 预估费用
    -- ... 更多计费和统计列，共约 25 列
);

CREATE TABLE messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,  -- 同时作为 FTS5 rowid
    session_id TEXT NOT NULL,
    role TEXT NOT NULL,          -- user / assistant / tool
    content TEXT,                -- 消息文本（FTS5 索引此列）
    timestamp REAL NOT NULL,
    tool_calls TEXT,             -- JSON 序列化
    reasoning TEXT               -- 推理链文本（v6 新增）
);

-- FTS5 全文搜索虚拟表
-- ⚠ 注意：FTS5 默认使用 unicode61 tokenizer，对中文连续文本（如"项目结构"）
--   无法识别词边界，整段短语被当作一个 token；搜索子词（如"结构"）可能无法命中。
--   中文搜索建议用空格分隔单字：搜 "项目 结构" 而非 "项目结构"。
CREATE VIRTUAL TABLE messages_fts USING fts5(
    content,               -- 消息文本
    session_id UNINDEXED,  -- 所属会话
    role UNINDEXED,        -- user/assistant/tool
    timestamp UNINDEXED
);
```

**检索与写入时序**：

```
[写入]
run_conversation() 结束时：
    _persist_session(messages, conversation_history)
        │
        ├── 增量写入新消息到 messages_fts
        └── 更新 sessions 表（创建时间、模型、标题等）

[检索]
LLM 调用 session_search(query="上次 Docker 问题", limit=5)
    │
    └── state.db FTS5 查询（跨所有 session 全库搜索，无 session_id 过滤）
            │  SELECT content, session_id, started_at
            │  FROM messages_fts
            │  WHERE content MATCH 'Docker 问题'
            │  LIMIT 5
            ▼
        返回相关历史片段 + 时间戳 + 来源平台
        → LLM 直接复用历史上下文，无需用户重新说明
```

**压缩后的 session 链表**：每次上下文压缩时，旧 session 被封存（`end_session()`），新 session 通过 `parent_session_id` 链接父会话，形成单向链表。封存后的旧 session 消息一行不动，`session_search` 的全库搜索可以命中所有历史 session 的原始内容——即使已经历多次压缩，第一个 session 的完整原始消息仍然可搜。

```
session_A（原始）
  ├── 存有 N 条完整原始消息（永久冻结）
  ├── ended_at = <时间戳>，end_reason = "compression"
  └── parent_session_id = NULL（根节点）
         ↑ parent_session_id
session_B（第一次压缩续接）
  ├── 存有压缩后的续接消息
  └── parent_session_id = session_A
         ↑ parent_session_id
session_C（进行中）
  ├── ended_at = NULL（进行中）
  └── parent_session_id = session_B
```

**对话数据会永久保存吗？有自动清理吗？** 会话数据**默认永久保留，没有自动 TTL 清理**。用户需手动调用清理命令（只删除已结束的会话，进行中的 active session 不受影响；被删除的 session 的 child sessions 会被孤立化而非级联删除）：

```bash
# 清理 90 天前已结束的会话（默认值）
hermes sessions prune --older-than 90

# 清理 30 天前的会话
hermes sessions prune --older-than 30 --yes

# 只清理某个平台来源的旧会话
hermes sessions prune --older-than 60 --source telegram
```

**多平台（CLI、Telegram、Discord）之间的记忆是共享还是隔离的？** 默认**共享**（同一 profile 下所有平台读取相同的 `HERMES_HOME`）。`sessions` 表中有 `source` 字段区分来源，`session_search` 默认跨所有 source 搜索，也可指定 source 过滤。若要隔离，为不同平台使用不同 profile（`hermes -p telegram_bot gateway start`）即可做到记忆、历史、配置完全独立。

```
├── hindsight/      # 本地 CLI hindsight 工具（事后回顾）
└── openviking/     # 开源向量记忆（自托管，隐私优先）
```

**与内置记忆的关键区别**：

| 维度 | 内置记忆（MEMORY.md） | 外部记忆（Mem0 等） |
|---|---|---|
| 注入位置 | system prompt（冻结快照） | user 消息末尾（动态 prefetch） |
| 检索方式 | 全量注入 | 按当前问题语义相似度检索 |
| 更新时机 | LLM 主动调用 memory 工具 | 提供商 SDK 自动管理 |
| 缓存友好 | 是（system 前缀不变） | 是（注入 user 消息不影响 system） |

**外部记忆为什么注入 user 消息而非 system prompt？**

外部记忆的 recall 结果是动态的（每次请求不同），若注入 system prompt 则每轮都会破坏 Anthropic prefix cache。注入到当前轮 user 消息末尾，system 前缀保持稳定。

```python
# run_agent.py：整轮只 prefetch 一次
_ext_prefetch_cache = memory_manager.prefetch_all(original_user_message)

# 组装 api_messages 时动态注入（不污染 messages）
if idx == current_turn_user_idx and _ext_prefetch_cache:
    _fenced = build_memory_context_block(_ext_prefetch_cache)
    api_msg["content"] = base_content + "\n\n" + _fenced
```

**外部 Provider 与内置记忆是并行运行还是互斥？** 两者**并行运行，但外部 Provider 互斥注册**：内置记忆（`BuiltinMemoryProvider`）始终先注册、不可移除；外部 Provider 任意时刻最多允许一个（尝试注册第二个会发出警告并被拒绝，以防止工具 schema 膨胀和记忆后端冲突）。两种记忆同时对 LLM 可见，各司其职：内置记忆通过 `memory` 工具由 LLM 主动调用，注入 system prompt 冻结快照；外部 Provider 通过 `prefetch/sync_turn` 后台运行，注入 user 消息末尾动态上下文。

### MemoryProvider 接口与 MemoryManager 架构

#### MemoryProvider 抽象基类（agent/memory_provider.py）

所有外部记忆提供商都必须实现 `MemoryProvider` 抽象基类，定义统一接口：

```python
# agent/memory_provider.py
class MemoryProvider(ABC):
    @property
    @abstractmethod
    def name(self) -> str: ...          # 提供商名称（如 "mem0"）

    @abstractmethod
    def is_available(self) -> bool: ... # 环境变量 / 依赖检查

    def initialize(self, session_id: str, **kwargs) -> None:
        """会话开始时调用，初始化上下文（可选实现）"""

    def system_prompt_block(self) -> str:
        """返回注入 system prompt 的静态说明文字（如提供商名称/使用建议）"""
        return ""

    def prefetch(self, query: str, *, session_id: str = "") -> str:
        """每轮 API 调用前：同步拉取相关记忆，返回文本块（阻塞）"""
        return ""

    def queue_prefetch(self, query: str, *, session_id: str = "") -> None:
        """本轮结束后：后台预加载下一轮可能用到的记忆（非阻塞）"""

    def sync_turn(self, user_content: str, assistant_content: str,
                  *, session_id: str = "") -> None:
        """每轮对话结束后：将本轮内容异步写入提供商（非阻塞）"""

    @abstractmethod
    def get_tool_schemas(self) -> List[Dict[str, Any]]:
        """返回提供商暴露给 LLM 的工具 Schema 列表（无工具则返回 []）"""

    def handle_tool_call(self, tool_name: str, tool_args: dict, **kw) -> str:
        """处理 LLM 发出的工具调用（仅当 get_tool_schemas 非空时需实现）"""
        return ""

    def shutdown(self) -> None:
        """会话结束时清理资源（可选实现）"""
```

#### MemoryManager 编排层（agent/memory_manager.py）

`MemoryManager` 统一管理多个 Provider 的生命周期：

```python
# agent/memory_manager.py
class MemoryManager:
    def add_provider(self, provider: MemoryProvider):
        """注册一个外部记忆提供商"""

    def initialize_all(self, session_id: str, **kwargs):
        """初始化所有已注册 Provider"""
        for p in self._providers:
            p.initialize(session_id, **kwargs)

    def build_system_prompt(self) -> str:
        """聚合所有 Provider 的 system_prompt_block（注入 system prompt）"""

    def prefetch_all(self, query: str, *, session_id: str = "") -> str:
        """阻塞式聚合所有 Provider 的 prefetch 结果（每轮 API 调用前）"""

    def queue_prefetch_all(self, query: str, *, session_id: str = "") -> None:
        """并发触发所有 Provider 的后台预加载（每轮结束后）"""

    def sync_all(self, user_content: str, assistant_content: str,
                 *, session_id: str = "") -> None:
        """并发触发所有 Provider 的后台写入（每轮结束后）"""

    def get_all_tool_schemas(self) -> List[Dict[str, Any]]:
        """聚合所有 Provider 的工具 Schema，合并进 tool_schemas 列表"""
```

**prefetch_all 的超时与容错**：`prefetch_all()` 本身是同步调用，超时控制在各 Provider 的 `prefetch()` 实现内部（可通过 `auxiliary.{task}.timeout` 配置，默认 30 秒）。采用**防御性调用**——单个 Provider 失败（超时/网络错误）不阻塞其他 Provider，`except Exception` 捕获后记录 debug 日志继续下一个 Provider，不影响 API 调用主流程：

```python
# agent/memory_manager.py - prefetch_all()
for provider in self._providers:
    try:
        result = provider.prefetch(query, session_id=session_id)
        if result and result.strip():
            parts.append(result)
    except Exception as e:
        logger.debug("Memory provider '%s' prefetch failed (non-fatal): %s", provider.name, e)
        # 吞掉异常，继续下一个 Provider
return "\n\n".join(parts)  # 汇总所有成功结果
```

## 各轮次记忆行为详解

**结论先行**：首轮和后续轮次在记忆行为上有三处关键差异——外部 Provider prefetch 首轮为空、SQLite 首轮无可用历史（但 `session_search` 随时可调）、`queue_prefetch` 首轮后才开始预热。下表和逐轮时序图给出完整说明。

| 机制 | 第 1 轮（首轮） | 第 2 轮 | 第 N 轮（稳态） |
|---|---|---|---|
| 外部 Provider prefetch | 空（无上轮 queue_prefetch 缓存） | 返回第 1 轮结束时 queue_prefetch 预热的结果 | 返回上一轮结束时预热的结果（完整缓存命中） |
| SQLite FTS5（session_search） | 可调用（检索历史 session）；本轮消息尚未写入，当前轮不可搜 | 第 1 轮消息已持久化，可搜；LLM 主动调用时才触发 | 前 N-1 轮消息全部可搜；LLM 按需调用 |
| _persist_session（写入 SQLite） | 本轮结束后写入；写入前当前轮消息不可搜 | 本轮结束后增量写入（仅追加新消息） | 同上，增量追加 |
| 内置记忆（MEMORY.md） | 已注入 system prompt（冻结快照），LLM 从第一条消息起即可读取 | system prompt 不变；LLM 写入的新记忆仍不在快照中 | 同上；新记忆下次会话才进快照 |
| 外部 Provider sync_turn（写入） | 本轮结束后后台线程写入；第 2 轮 prefetch 可能已含本轮内容（取决于写入速度） | 同上 | 同上（后台异步，不阻塞主流程） |

```
────────────────────────────────────────────────────────────────
会话开始（AIAgent.__init__）
  MEMORY.md + USER.md → 冻结注入 system prompt
  外部 Provider initialize()
────────────────────────────────────────────────────────────────

【第 1 轮】
  用户发送消息
  │
  ├─ prefetch_all(user_msg)
  │    → _prefetch_cache 为空（无上轮预热）
  │    → 外部记忆注入 = ""（首轮无外部记忆）
  │
  ├─ API 调用（携带 system prompt 冻结快照 + 空外部记忆）
  │    LLM 可主动调用 session_search → 检索历史 session
  │    ⚠ 当前轮消息尚未写入 SQLite，本轮内容不可搜
  │    LLM 可主动调用 memory 工具 → 写入 MEMORY.md（当前快照不更新）
  │
  └─ 轮后
       sync_all()          → 后台写入外部 Provider（mem0 等）
       queue_prefetch_all()→ 后台预热：以本轮 user_msg 为 query 预加载下一轮记忆
       _persist_session()  → 第 1 轮消息写入 SQLite（第 2 轮起可搜）

────────────────────────────────────────────────────────────────

【第 2 轮】
  用户发送消息
  │
  ├─ prefetch_all(user_msg)
  │    → 返回第 1 轮 queue_prefetch 预热的缓存结果
  │    → 外部记忆注入到本轮 user 消息末尾（首次有内容）
  │
  ├─ API 调用
  │    第 1 轮消息已在 SQLite，LLM 调用 session_search 可检索
  │    LLM 可读取注入的外部记忆上下文
  │
  └─ 轮后（同第 1 轮逻辑，循环执行）

────────────────────────────────────────────────────────────────

【第 N 轮（稳态）】
  prefetch_all    → 上轮 queue_prefetch 预热结果（完整缓存命中）
  session_search  → 前 N-1 轮消息全部可搜（LLM 按需调用）
  内置记忆快照    → 始终为会话开始时的冻结版本（不随写入更新）
  sync_turn       → 后台异步写入，不阻塞当前轮
  _persist_session→ 本轮结束后增量追加到 SQLite

────────────────────────────────────────────────────────────────

【上下文压缩触发时（任意轮次）】
  flush_memories()    → 辅助 LLM 扫描对话，按需写入 MEMORY.md
  _compress_context() → 压缩 messages + 创建新 session（旧 session 冻结保留）
  self.session_id 换新，Agent 对象原地复用，不重建
```

**关于"首轮不会调用 SQLite FTS5"**：这个说法需要拆分理解。`session_search` 是工具，首轮 LLM 完全可以主动调用它检索历史 session——只要 LLM 判断"需要回忆过去"就会触发。首轮"没有"的，是**当前轮自身的消息在 SQLite 中不可搜**（因为 `_persist_session` 在轮后才执行）；以及**外部 Provider prefetch 返回空**（因为没有上轮的 `queue_prefetch` 缓存）。这是两件完全不同的事。

## FAQ

### 会话历史的持久化与 Session 链表

**结论**：SQLite 里存的是"混合版本"——既有压缩前的完整原始对话，也有压缩后的续接对话。关键在于压缩时只创建新 session、旧 session 只打时间戳标记不删任何消息。

### 压缩时的 Session 封存机制

```python
# hermes_state.py
def end_session(self, session_id: str, end_reason: str) -> None:
    """Mark a session as ended."""
    conn.execute(
        "UPDATE sessions SET ended_at = ?, end_reason = ? WHERE id = ?",
        (time.time(), end_reason, session_id),  # 只写两个字段，消息一条不动
    )
```

每次压缩时，`_compress_context()` 执行 session 拆分：

```python
# run_agent.py
self._session_db.end_session(self.session_id, "compression")  # 旧 session 封存（保留全量消息）
old_session_id = self.session_id

self.session_id = new_session_id                              # 生成新 session_id
self._session_db.create_session(
    session_id=self.session_id,
    parent_session_id=old_session_id,                         # 用 parent_session_id 链接父会话
)
self._last_flushed_db_idx = 0                                 # 新 session 游标归零
```

### 压缩后是新建 Agent 还是复用原 Agent？

**完全复用原 Agent 对象**，`self` 不变，只有四处状态变化：

```python
# _compress_context() 内部
self.context_compressor.compress(messages)  # ① 内存中压缩 messages 列表
self._session_db.end_session(旧id)           # ② SQLite：旧 session 封存
self.session_id = 新id                       # ③ 只改这一个属性
self._session_db.create_session(新id, parent_session_id=旧id)
self._last_flushed_db_idx = 0               # ④ 重置写入游标
```

调用方接收返回值后**原地替换局部变量**，Agent 对象本身不重建：**不需要重走 **`**AIAgent.__init__()**`**，不重新加载工具，不重建 system prompt，不重新注册 Provider**。是原 Agent 对象在原循环内继续跑，只是 `messages` 这个局部变量被换成了更短的列表，只有 `self.session_id` 换了一个新 id。

### 上下文超限的三道防线

```
run_conversation() 主循环
│
├── [进入前] 预检压缩（preflight）
│       messages 过长 → _compress_context() → messages 缩短
│       self.session_id 换新，其余 Agent 状态不变
│       继续进入主循环 ↓
│
├── [每轮结束] 正常压缩（主循环内，50% 阈值触发）
│       API 返回 prompt_tokens → should_compress() → True
│       → _compress_context() → messages 缩短，session_id 换新
│       → continue（同一个循环，同一个 Agent 继续）
│
└── [API 报错] 强制压缩（硬溢出兜底）
        413/context-too-large → 先降档（调低 context_length）
        → 强制 _compress_context() → 重试当前轮 API 调用
        → 超过 max_compression_attempts → 返回 error，终止
```
