# 六、上下文压缩

LLM 的上下文窗口是有限的。一个长期运行的 Agent（处理复杂编码任务、多步骤研究）在数百轮对话后，messages 列表的 token 总量会轻松超过 100K，触碰模型的硬限制。

Hermes 的上下文工程要解决的核心问题是：**在有限的上下文窗口里，如何最大化保留对"继续完成任务"最重要的信息**。

答案是**中部压缩**：任务的起点（用户目标）和最近的进展（尾部）都要保留，被压缩掉的是中间那些已经完成的工具调用历史——它们的具体内容已经不再重要，只需要一份结构化摘要告诉 LLM"我们之前做了什么"。

## FAQ

### 为什么在 50% 时触发，而不是 90%？

这是一个**主动容错**设计，而非保守设计：

```
情景：模型 context = 200K tokens，工具 schema = 25K tokens

若在 90% 触发：
  检查时：~180K tokens（低于阈值）
  工具执行后工具结果追加：+15K tokens
  下一次 API 调用总量：~195K tokens
  → 超过 200K → API 报 context_length_exceeded（4xx）
  → 4xx 被判定为不可重试错误 → 对话直接中断！

若在 50% 触发（当前设计）：
  检查时：~100K tokens（触发）
  压缩后：~30K tokens
  → 有大量余量继续工具调用
  → 用户看到"⟳ compacting context…"提示，体验流畅
```

### 如何计算Token 

Hermes 优先使用 API 响应中的真实 token 计数，而不是估算：

```python
# 优先：API 返回的真实值（最准确）
if _compressor.last_prompt_tokens > 0:
    _real_tokens = last_prompt_tokens + last_completion_tokens

# 回退：粗略估算（API 断连后 usage 数据为 0 时）
else:
    _real_tokens = estimate_messages_tokens_rough(messages)
    # ⚠️ 关键：若 API 断连，usage=0
    # 若用 should_compress(0)，则 0 < threshold → 永远不压缩
    # → 会话无限膨胀，下次调用必然 4xx（已知 bug #2153）
```

### 结构化摘要：信息的精华提炼

压缩时调用辅助 LLM 生成的摘要，遵循一个固定模板，保证信息的完整性：

```
## Goal
[用户原始目标是什么]

## Constraints & Preferences
[用户偏好、约束、重要决策]

## Progress
### Done
[已完成的工作——包含具体文件路径、命令、结果]
### In Progress
[进行中的工作]
### Blocked
[遇到的阻碍]

## Key Decisions
[重要技术决策和原因]

## Relevant Files
[读取/修改/创建的文件，附简短说明]

## Next Steps
[接下来应该做什么]

## Critical Context
[不能丢失的具体值：错误信息、配置参数、端口号、API 地址等]

## Tools & Patterns
[使用了哪些工具、哪些命令是有效的]
```

**为什么用这个模板，而不是让 LLM 自由发挥？**

自由发挥容易产生"文学性摘要"，听起来流畅但缺少具体信息（文件路径、命令、错误信息等）。结构化模板强制 LLM 保留这些"不能丢失的细节"，让下一个 context 里的 Agent 可以真正接续工作，而不是重复劳动。

### 压缩完之后可能存在哪些问题

压缩会切割消息列表，可能在边界处产生"孤儿"——一个 tool_call 的结果消息被切掉了，或者一个 tool_result 对应的调用消息被摘要替换了。OpenAI 和 Anthropic API 都要求 tool_call / tool_result 必须成对出现，否则报 400 错误。

### 预检压缩（进入循环前）机制

除了在循环中的动态检查，Hermes 还在 `run_conversation()` 入口处做一次预检：

```
场景：用户在 CLI 切换到上下文更小的模型，但已有一个大体量会话历史

预检步骤：
  estimate_request_tokens_rough(messages + system_prompt + tool_schemas)
                                           ↑
                               工具 schema 约占 20-30K token，
                               旧版估算经常漏掉这部分
  
  若超过阈值 → 预检压缩（最多 3 轮，直到降至阈值以下）

好处：避免"第一次 API 调用就超限报错"
     在有余量时主动压缩，体验更好
```

## 压缩后 messages 的结构

### 压缩前后对比

压缩前，messages 列表是完整的多轮对话历史：

```
压缩前 messages：
  [0] role: system    → "你是 Hermes..."
  [1] role: user      → "帮我重构 file_tools.py"       ← 头部保留（protect_first_n=3）
  [2] role: assistant → "好的，先读一下文件..."         ← 头部保留
  ──────── 以下是"中间段"，被压缩掉 ────────
  [3] role: tool      → "文件内容: def read_file..."
  [4] role: assistant → "我看了代码，建议..."
  [5] role: user      → "好，继续"
  [6] role: assistant → tool_calls: [write_file(...)]
  [7] role: tool      → "写入成功"
  ... 十几二十轮 ...
  ──────── 以下是"尾部"，最近约20K token，原样保留 ────────
  [N-2] role: user      → "现在帮我加单测"
  [N-1] role: assistant → "好的，我来写测试..."
  [N]   role: tool      → "test_file_tools.py 写完"
```

压缩后，中间 N 条消息被**替换为 1 条摘要消息**：

```
压缩后 messages：
  [0] role: system    → "你是 Hermes...\n\n[Note: Some earlier conversation turns
                         have been compacted...]"    ← 第一次压缩追加了注释
  [1] role: user      → "帮我重构 file_tools.py"    ← 头部，原样保留
  [2] role: assistant → "好的，先读一下文件..."      ← 头部，原样保留

  [3] role: user      → "[CONTEXT COMPACTION] Earlier turns in this conversation
                         were compacted to save context space. The summary below
                         describes work that was already completed...
                         ## Goal
                         用户想重构 file_tools.py 并提升性能
                         ## Progress
                         ### Done
                         - 读取了 file_tools.py（共 423 行）
                         - 重写了 read_file()，添加了 offset/limit 参数
                         ### In Progress
                         - 正在为重构后的代码编写单测
                         ## Relevant Files
                         - tools/file_tools.py: 主要重构目标，已完成
                         ..."                       ← 摘要消息（1条替换了N条）

  [4] role: user      → "现在帮我加单测"            ← 尾部，原样保留
  [5] role: assistant → "好的，我来写测试..."        ← 尾部，原样保留
  [6] role: tool      → "test_file_tools.py 写完"   ← 尾部，原样保留
```

### system prompt 的特殊处理

**第一次压缩时**，system prompt 会追加一行注释（仅此一次，后续压缩不再重复追加）：

```python
# agent/context_compressor.py compress()
if i == 0 and msg.get("role") == "system" and self.compression_count == 0:
    msg["content"] = (
        (msg.get("content") or "")
        + "\n\n[Note: Some earlier conversation turns have been compacted into a "
          "handoff summary to preserve context space. The current session state "
          "may still reflect earlier work, so build on that summary and state "
          "rather than re-doing work.]"
    )
```

### 摘要消息的 role 选择逻辑

摘要消息插在头部和尾部之间，其 role 会动态选择，避免与相邻消息的 role 冲突（OpenAI 要求 user/assistant 交替出现）：

```python
# 优先避免与头部最后一条 role 冲突，其次避免与尾部第一条冲突
if last_head_role in ("assistant", "tool"):
    summary_role = "user"
else:
    summary_role = "assistant"
# 如果和尾部仍冲突，且翻转不影响头部，则翻转
if summary_role == first_tail_role:
    flipped = "assistant" if summary_role == "user" else "user"
    if flipped != last_head_role:
        summary_role = flipped
    else:
        # 两侧都冲突 → 将摘要合并到尾部第一条消息的开头
        _merge_summary_into_tail = True
```

## 如何查看被压缩的内容？

压缩后原始历史**并没有被删除**，只是不在 active messages 里了。有两种方式找回：

### 方式 1：直接问 Agent（LLM 能看到摘要）

摘要消息本身就在 messages 里，LLM 下一轮即可读到。直接对话：

```
用户："你之前做了什么？"
Agent：从摘要消息里读取，回答"我们已经完成了 X、Y、Z..."
```

### 方式 2：查 SQLite + JSON 文件（完整原始记录）

压缩时，旧 session 在 SQLite 里被打上 `"compression"` 标记并结束，同时创建新 session id。完整原始对话保存在：

```python
# run_agent.py _compress_context()
self._session_db.end_session(self.session_id, "compression")  # 旧会话归档，完整历史保留
self.session_id = f"{datetime.now()...}_{uuid4()...}"         # 创建新会话 id
```

- **SQLite**：`~/.hermes/sessions.db`，可通过 `/history` 命令检索
- **JSON 文件**：`~/.hermes/logs/session_<旧session_id>.json`，包含压缩前的完整 messages

> 原始记录永远不会被物理删除——压缩只影响 active messages（当前 API 调用传入的 messages 列表），不影响持久化存储。`/history` 命令或直接读 JSON 文件即可回溯所有历史对话。
